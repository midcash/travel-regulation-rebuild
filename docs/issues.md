# 问题记录与后续业务优化

本阶段优先跑通 observation 原有的 agent loop、可观测性、评测与三个页面。按用户最新要求：子智能体后续返回的问题只记录，留待下一次会话讨论，不继续修正或扩大本阶段范围。

## 已发现的问题

以下四项在用户提出“后续只记录”的要求之前已经修改并通过本地回归，保留记录以便审阅。

1. 未查询工具便直接返回无可行方案，曾被运行时接受，部分负例也可能误通过。已要求失败结论之前查询四类工具，并在评测中独立检查查询记录与证据。
2. 评测曾只验证 ID、时间及总额，漏检合法 ID 下改换座席、交通方式、酒店标签或挪动单项价格。已增加独立 oracle 行程快照比较；后续接入真实 API 时需要改为适合动态供应数据的语义断言，不应继续强制固定记录。
3. 极端日期转换可能抛出 OverflowError。已转换为输入错误，HTTP 返回 400；日期范围与自然语言时间解析的产品约定留到后续。
4. Trace 原来只显示 budget_exceeded，不能区分步骤、工具、Token 或总时限耗尽。已记录 budget_reason 和 Span 的 budget.reason。

开发中还发现 Windows 上 SQLite 连接未显式关闭导致文件占用，已在用户最新要求之前修复。

## 留到后续讨论的业务范围

- 当前只有杭州 → 上海东方明珠塔的固定数据和单一酒店；其他输入没有可行方案，不代表现实中不存在可行路线。
- 默认会议前一晚 18:00 起出发；暂不做自然语言“下周六”的解析、候选方案搜索、当天出发等策略。
- 单条行程、政策限额、提前到达量、模拟时长和费用均为演示规则，等待用户审阅，不在本阶段继续优化。
- 不计算出发地到车站及站内时间；真实四类业务 API、路线真实性与动态报价属于后续接入范围。
- 失败文案目前只区分无可行方案、资料不足、执行未完成，暂不细分每一条业务不可行原因。

初轮真实模型曾忽略到达截止时间并重复查询超时工具。通过业务提示词明确比较 end_at 与截止时间、按优先级结束后，两轮六案例回归通过。保留失败 Trace 和旧评测批次用于对比；此结果仅说明固定演示案例通过，不代表开放业务场景的准确率。

## 独立复查收尾

子智能体对上述四个原始复现进行了只读复查：无查询拒绝、记录篡改、极端日期、预算原因四项均确认原问题不再成立，未报告新增问题。用户要求“只记录”之后，主代理未再修改业务实现。
