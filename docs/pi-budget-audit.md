## 80k 是否包含命中、是否调整

**80,000 是一次用户请求所属 run 的累计用量，包含缓存命中的输入**。逐请求累加 `input + cacheRead + cacheWrite + output`；有原始用量时与 `prompt_tokens + completion_tokens` 交叉校验，reasoning 已在 output 中不重复加。命中改变价格，不从 token 预算扣除。它不是上下文窗口，也不是仅未命中 token。原始接口未独立报告 cache-write，本批规范化 cacheWrite=0 不能证明写缓存收费为零；中断未知用量不能填零。

初始预算本轮不直接改值：仍为 **模型 12 / 工具 20 / HTTP 30 / 累计 token 80,000 / 活跃 180 秒 / 单模型 45 秒**，均待后续校准。完整工具覆盖回放最高 36,487，全部正式样本最高 49,196；80k 分别约为 2.19 倍、1.63 倍。最高样本乘 1.25 再加下一回答 4,096 为 65,591，只说明这些已测短历史样本未触限，不能推断多轮后段足够。上下文 30k 连续三次请求即至少 90k 输入，42k 连续两次即至少 84k，尚未含输出；即使全部缓存命中也照计，80k 很可能拦下这类请求。工具尚漏记 SDK 前置拒绝，HTTP/时延是历史投影，也不能据此保证在线流程预算够用。

## M03b 前的预算门禁

采用方案 a，不采用方案 b：缓存命中输入继续计入累计 token；缓存状态改变价格，不改变统一用量口径，避免隐藏长历史反复提交的成本。M01 实现受控配置、含缓存的全尝试计量和逐次预算预检，执行中不得自动加额；恢复/后续轮同样检查历史输入。

M04b 保留完整覆盖三亚回放和三类改口各 3–5 次，并补多轮后段：待发上下文 30–36k、42–48k 两档，分别覆盖 B05 式修改查询、B08 式服务重启恢复后查询、B09 式隔日当前价格核验；每档每种情境至少三次，共至少十八次，每次需查询，目标覆盖 2–3 次业务模型调用，压缩额外计数，实际更多也保留。采用相关历史消息/工具/选定证据/压缩记录，不能用无关填充凑长度；准备历史与后段请求分别计量。实际阈值 T 小于 48k 时等比例取 T 的 62.5%–75%、87.5%–100%，记录实际长度。报告每次待发上下文、命中/未命中输入与输出、压缩/摘要成本、调用次数和被拦截情况，不能筛掉失败。

首轮、改口、多轮后段进入同一门禁：模型/工具/历史 HTTP/token 最大样本乘 1.25 不超过配置，token 再加下一回答 4,096 预留。后段被预算拦下即失败，不能当完整用量或剔除；先有据调整预算或压缩配置，记录前后值并重测受影响样本，再允许 M03b，不在执行中自动加额。

**活跃时间 180 秒无法用回放校准，真实供应商耗时在 M03b 首次验证。** M04b 仅记录回放耗时，不用它通过真实时间门禁。若 M03b 超时，门禁失败、不切换默认入口，按实测调整受控时间配置并记录前后值及依据，重跑完整真实验收。任意供应商失败或模型随机性仍可能触限，不能记验收通过。

结论：短历史样本不证明多轮后段的 80k 足够。M04b 必须补测并通过 token/调用门禁；真实完整三亚及 180 秒耗时门禁在 M03b 验证，新在线实测须单独报告，不能用十二次累计或假模型 token 替代。本轮只修订样本与门禁，没有执行这些测试或开始 M01。
