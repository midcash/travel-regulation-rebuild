## 形状

**MCP 客户端就是三步，每一步都只是 `_call(method, params)`。**

```python
def _call(self, method, params=None) -> Response:      # ★ 唯一的往返出口
    self._next_id += 1                                 # id 由客户端自己发号
    request = Request(method=method, params=params or {}, id=self._next_id)
    return self.transport.send(request)                # ★ 换传输只改这一行

def initialize(self):                                  # ① 握手
    response = self._call("initialize", {"protocolVersion": "2025-06-18",
                                         "capabilities": {}, "clientInfo": {...}})
    self.server_info = response.result or {}           # 全程没提工具，对面有什么还不知道
    # ← 到这一步为止，一个工具都还不知道

def list_tools(self):                                  # ② 发现
    response = self._call("tools/list")                # 空 params：信封里干脆没这个键
    self.tools = (response.result or {}).get("tools", [])
    # ★ 工具名到这里才第一次出现

def call_tool(self, name, arguments):                  # ③ 调用
    response = self._call("tools/call", {"name": name, "arguments": arguments})
    if not response.ok:
        return ToolCallResult(ok=False, protocol_error=response.error)   # 协议级
    is_error = bool((response.result or {}).get("isError"))              # 业务级
```

**服务端就是一个查表。**

```python
def handle(self, request) -> Response:
    handler = self.handlers.get(request.method)        # ★ 查表；没有 → -32601
    try:
        result = handler(request.params)
    except ProtocolError as exc:                       # 协议级 → 顶层 error 字段
        return Response(id=request.id, error=Error(exc.code, exc.message, exc.data))
    except Exception as exc:                           # 兜底 → -32603，服务端不因一个请求崩掉
        return Response(id=request.id, error=Error(INTERNAL_ERROR, ...))
    return Response(id=request.id, result=result)
```

### JSON-RPC 信封的真实长相

```
① initialize（握手）
   → {"jsonrpc":"2.0","method":"initialize","id":1,
      "params":{"protocolVersion":"2025-06-18","capabilities":{},
                "clientInfo":{"name":"travel-host","version":"1.0.0"}}}
   ← {"jsonrpc":"2.0","id":1,
      "result":{"protocolVersion":"2025-06-18",
                "capabilities":{"tools":{"listChanged":true}},
                "serverInfo":{"name":"travel-kb","version":"1.0.0"}}}

② tools/list（发现）
   → {"jsonrpc":"2.0","method":"tools/list","id":2}          ← 注意：没有 params 键
   ← {"jsonrpc":"2.0","id":2,"result":{"tools":[
        {"name":"query_knowledge",
         "description":"在指定集合里检索答案。返回带来源引用的可读文本，不是裸 JSON。",
         "inputSchema":{...}, "outputSchema":{...},
         "annotations":{"readOnlyHint":true, "destructiveHint":false,
                        "idempotentHint":true, "openWorldHint":false}}]}}

③ tools/call（调用）
   → {"jsonrpc":"2.0","method":"tools/call","id":3,
      "params":{"name":"query_knowledge",
                "arguments":{"collection":"travel_policy","question":"退票要手续费吗"}}}
```

**错误有两个完全不同的位置 —— 这是全章最该记住的一点：**

```
协议级（参数非法 / 工具不存在）→ 顶层 error 字段，连 result 键都没有
   {"jsonrpc":"2.0","id":4,
    "error":{"code":-32602,"message":"没有名为 'no_such_tool' 的工具",
             "data":{"availableTools":["list_collections","describe_collection","query_knowledge"]}}}

业务级（查询失败）→ 在 result **里面**
   {"jsonrpc":"2.0","id":6,
    "result":{"content":[{"type":"text","text":"查询失败：在集合 'member_rules' 里没有找到…"}],
              "isError":true}}
```

### 理论 → 代码 对照

| 笔记第 4 章的说法 | 代码里的真实形状 | 反直觉 / 容易漏掉 |
|---|---|---|
| Host / Client / Server 三层 | `MCPToolkit` / `MCPClient` / `MCPServer` | `host.py` 里**没有任何 LLM 调用**；Host 层的全部内容是**字段名翻译** |
| 动态能力更新，无需重写客户端 | 服务端整体替换 `descriptors`，客户端再发一次 `tools/list` | **不是推送**——见下面第③点 |
| 本地 Server 用 stdio 传输 | 两种传输共用 `send(request) -> Response` | 同进程的实现只有一行 `return self.server.handle(request)` |
| 两层错误机制 | 协议级 → `error` 字段；业务级 → `result.isError` | **两条路径都带 `isError` 键**（成功时是 `false`） |
| 出参要结构化 + 附带纯文本 | `result` 里同时有 `content`（文本）和 `structuredContent` | 两者**真的都返回了**，不是二选一 |
| 入参约束内联 | `inputSchema` 里的 `default` / `minimum` / `maximum` / `enum` | 服务端 `_validate` **真的会用 `default` 补值**，不只是声明 |

### 最反直觉的四个点

**① 「工具不存在」返回的是 `-32602`，不是 `-32601`**

`protocol.py:34` 里 `TOOL_NOT_FOUND = INVALID_PARAMS`（都等于 `-32602`）。

直觉上 `-32601` 的常量名就叫 `METHOD_NOT_FOUND`，最该用它。但这份实现把
`-32601` 严格留给「未知的 JSON-RPC 方法名」——因为**工具名是 `tools/call`
的参数**（`params["name"]`），不是方法名，所以「工具不存在」被归成
「你这次请求不对」。

> **推论：按 `-32601` 去 grep 工具相关的错误，一条都找不到。**

**② 判断业务成败不能看 `isError` 在不在，只能看它的值**

成功路径也写死了 `"isError": False`（`server.py:238`），失败路径是 `True`。
两条路径**都带这个键**。

而且失败的说明文字不在什么 `errormessage` 字段里——它在
`result.content[0].text`，客户端还得自己过滤出 `type == "text"` 的元素再拼。

**③ 握手只有一次往返，客户端声明的能力是空字典**

```python
"capabilities": {},          # client.py:152 —— 客户端什么能力都没声明
```

服务端倒是声明了 `{"tools": {"listChanged": true}}`（`server.py:125`），
但**全仓库没有任何代码读这个字段**。

所以演示 4 的「动态能力更新」不是服务端推给客户端的——
**是客户端主动再调一次 `list_tools()` 重新拉的**。

> 概念上「交换能力声明」听起来像双向协商；代码里它是**单向的自我介绍**，
> 而通知通道根本没实现。

**④ 演示 1~5 默认走的**不是** stdio，是同进程 —— 而这正是抽象的胜利**

```python
TRANSPORT = "in-process"   # main.py:39，默认值
```

课件里那句话原来写的是「演示 1~5 全程走的都是 stdio」，是错的。
但纠正它的时候会发现：**这个错误之所以不容易被发现，恰恰说明传输层抽象做对了** ——
客户端只认 `transport.send(request)`，两种传输在客户端看来完全一样，
所以"到底走的哪条"从输出上看不出来。

同进程传输的实现只有一行：

```python
def send(self, request): return self.server.handle(request)   # 连序列化都省了
```

好处是**断点能从客户端一路跟到服务端、中间不断** —— 这对一个教学原型是决定性的。
想看真实形态，把 `TRANSPORT` 改成 `"stdio"`：那会把 `server.py` 起成一个真的子进程，
用管道通信（演示 7 就是这么做的，不改常量也能看到）。

> **这一条其实是笔记 4.3 的活证明**：传输协议是 MCP 的**可替换件**。
> 代码里"换个传输只改一行"，就是笔记说的"本地用 stdio、远端用 HTTP"能成立的前提。

MCP是一种标准化接口协议，统一了AI模型与外部资源的连接方式，用于让LLM能够访问外部的数据，工具和提示词。
MCP采用客户端-服务端架构，包含三个关键组件：Host，Client,和Server.其中Host是运行LLM的应用程序。Client MCP的典型优点是动态能力更新（工具参数变更时无需重写客户端代码），接口标准化（不同工具统一接入，减少开发成木的特占
成本)的特点。

## 4.3 MCP的传输协议

（最开始我复习的时候就是弄清楚了两种协议，本地：Stdio远端：SSE，这也是有一些视频这么讲的。但我在面试的时候，其实因为这个答案被挑战过，因为现在SSE在MCP里已经被替代了，所以我有了以下答案，相对来说这个答案是比较完整的，这题也是面试会考的题）MCP的传输协议针对于本地服务器和远端服务器有明显区别。
Server-SentEvents（SSE）来实现服务器实时推送，这种方式复杂且对网络稳定性要求高。新版本改为无状态协议，主要通过标准的GET和POSTHTTP请求完成交互，SSE变为可选增强功能，只有在需要实时推送时才启用。这一改动降低了实现复杂度，提高了兼容性和灵活性，使协议更接近REST风格，易于集成和扩展。
对于本地MCP Server，通常运行在开发者机器上，直接通过本地接口或STDIO（标准I/O）进行通信，不涉及网络传输，因此不需要复杂的认证或长连接管理。

## 4.4 MCPServerTool设计原则

来自真实面试问题。本身直接被问到倒是比较少，但是当你的项目，比如就是设计了MCP的Server，比如我们的RAG项目。这时候聊到你设置了哪些工具的时候，这个问题可能会被问到。
资料来源：MCP官方规范[modelcontextprotocol.io/specification/2025-06-18/server/tools]第一，入参设计一一参数最少化、类型严格、约束内联。LLM是根据inputSchema来构造参数的，schema本身是让LLM就是"给LLM看的说明书"。原则是：必填参数尽量少，能给默认值就给默认值，用枚举收敛可选项而不是让LLM自由发挥，类型要明确。约束直接写在schema里，比如最小值、最大值、默认值，这样Server端校验方便，LLM传参准确率也更高。我们项目里查询工具的返回条数参数就限定了范围和默认值，LLM不传就用默认值，传了超出范围直接截断。
第二，出参设计一一结构化返回，LLM友好。MCP规范支持outputSchema声明返回结构，让Client和LLM提前知道数据长什么样，做类型校验和自动解析。同时规范要求向后兼容一一结构化返回的同时要附带一个纯文本版本，保证老Client也能读。我们项目的做法是统一格式化输出，把检索结果转成带标题、来源引用、置信分数的可读文本，而不是丢裸JSON给LLM一一因为LLM读自然语言比读嵌套JSON效率高得多。
第三，错误处理一一双层错误机制，错误信息对LLM友好。MCP规范定义了两层错误：协议级错误用标准JSON-RPCerrorcode处理参数非法、tool找不到等问题；业务级错误通过isError:true加errormessage报告。关键原则是：错误信息要告诉LLM下一步该怎么办，而不是丢一堆堆栈。比如返回"集合不存在，可用的集合有A、B、C"，而不是返回Python异常堆栈。前者LLM能自主修正重试，后者只能把堆栈原样输出给用户看。
第四，ToolAnnotations一一声明副作用，让Client做安全决策。MCP规范定义了annotations字段，包含四个关键属性：是否只读、是否有破坏性、是否幂等、是否与外部世界交互。这些标注不影响执行逻辑，但Client会据此决定是否需要弹确认框。比如只读的查询工具可以自动执行，但有破坏性的删除工具就应该让用户二次确认。我们项目的三个tool全部是只读查询，都应该标注为只读。
第五，粒度控制一一单一职责，工具间可组合。MCP的设计是model-controlled一一LLM自己决定调用顺序和组合方式。所以工具拆分的粒度很关键：太粗LLM无法灵活组合，太细调用链路过长容易出错。我们项目拆了三个

tool：列出集合一查看文档详情→查询知识库，形成"先发现→再了解→最后查询"的自然工作流，上游的输出
可以直接作为下游的输入参数。
第六，安全与校验一一输入校验和输出脱敏。MCP规范明确要求Server必须校验所有输入、实现访问控制、限流、清洗输出。即使LLM传了符合schema的参数，Server端仍然要做业务层面的校验一一比如路径穿越检查、注入防护、敏感信息脱敏。同时规范强调"始终要有人类在回路中”，高危操作必须有确认机制。
总结来说，MCPtool的编写是"六位一体"的：description决定LLM能不能找到你，inputSchema决定传参准不准，outputSchema决定结果可不可解析，errorhandling决定失败后能不能自愈，annotations决定Client信不信
任你，粒度和安全则决定整个系统是否健壮可控。
