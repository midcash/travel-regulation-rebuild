## 形状

> 这是核心机制的骨架，不是完整代码。对应 `react_loop.py` 的 `ReActAgent.run()`。
> 省略号处是与形状无关的细节。

```python
messages = [{"role": "system", ...}, {"role": "user", user_input}]
tools = registry.schemas()

while True:
    response = llm.chat(messages, tools)          # ← Reasoning：模型干的
    messages.append(response.as_message())        # ① 先追加 assistant 消息

    if not response.tool_calls:                   # ② 唯一的正常出口
        return finish(response.content, "final_answer")

    for call in response.tool_calls:              # ③ 一轮可以调多个工具
        if signature(call) in seen_calls:         # ④ 跨轮累积的「无进展」检测
            repeated = True
        seen_calls.add(signature(call))
        result = registry.call(call.name, call.arguments)       # ← Act：框架干的
        messages.append(result.to_message(call.id, call.name))  # ← Observation：回注

    if repeated:                return finish(..., "repeated_call")
    if len(steps) >= max_steps: return finish(..., "max_steps")
```

**就这 15 行。** 生产代码里那几百行，绝大部分是在给这 15 行加东西：超时、
token 计数、异常分类、状态保存、可观测性。**形状本身只有这么多。**

### 三个角色谁干什么

笔记 9.2 把 ReAct 拆成 Reasoning / Act / Observation。在代码里它们分别是：

| 理论角色 | 代码位置 | 谁干的 |
|---|---|---|
| **Reasoning（推理）** | `llm.chat(messages, tools)` | 模型 |
| **Act（行动）** | `registry.call(name, args)` | **框架**（模型只*选*工具，不*执行*） |
| **Observation（观察）** | `messages.append(result.to_message(...))` | **框架** |

### 理论 → 代码 对照

| 笔记里的说法 | 代码里的真实形状 | 反直觉 / 容易漏掉 |
|---|---|---|
| 模型「决定」继续还是停止 | `if not response.tool_calls: return` | **模型从不说「我完成了」**，它只是这一次没给工具调用 |
| 「对话历史」 | `messages` 这一个数组 | 全部上下文就是这个数组；没有第二个状态 |
| 「有界循环」 | `while True` + 末尾 `if len(steps) >= max_steps` | 上界写在**循环体末尾**，不在 `range()` 里 |
| 「Agent Loop」 | 一个 `while` | 循环是**你写的**；模型只是循环体里的一次函数调用 |

### 最反直觉的两个点

**① 停止条件被编码进「返回值的形状」里，而不是一句显式的判断**

你想象中的流程是：模型判断「我该继续还是该回答」。

代码里没有这个判断。**模型给了 `tool_calls` 就继续，没给就结束。**
「决定」藏在返回值的结构里，不在任何一个 `if` 语句里。
（`react_loop.py:112`）

**② `messages.append(response.as_message())` 必须在工具执行之前**

顺序反不得。OpenAI 风格 API 要求**每条 `tool` 消息前面必须有一条带对应
`tool_call_id` 的 `assistant` 消息**。

这是**协议约束，不是风格选择**。（`react_loop.py:110`）

> 你自己在实验四的 README 里写过同一句话：「暂停点只能落在一个位置：
> assistant 消息已 append、对应 tool 消息未 append 之间……所以这是协议约束，
> 不是设计选择。」——**那就是这一行的必然结果。**

**③（附）用 `while True` 而不是 `for i in range(max_steps)`**

直觉上「有界循环」就该写成 `for`。但这里出口有**三个**（正常结束 / 重复调用 /
超轮次），写成 `for` 的话轮次用尽会**静默退出**，你分不清是「正常结束」还是
「被截断」——所以 `LoopResult.stopped_reason` 这个字段才必须存在。
（`react_loop.py:106`、`:143`）

# 9. ReAct

这是一个很简单的知识点，确实一个在各种框架里面都广泛运用的技术。这里讲的不多，但是都是精髓，配一个讲解视频，我觉得你应该可以理解这个概念。最常见的面试真题就是：ReAct如何实现的？我也附在了后面。
ReAct是Reasoning（推理）+Acting（行动）的结合。它让Agent在完成任务时交替进行推理和行动，并根据行动结果继续判断下一步。
其核心过程是：
代码块
Reason→Act→Observation→Reason→.→完成任务关键概念

·Reason（推理）：模型分析当前任务和已有信息，制定计划，或者根据上一次行动结果进行反思，判断下一步应该做什人
Act（行动）：模型决定调用某个工具，并提供调用工具所需的参数。
Observation（观察）：外部框架执行工具后返回的真实结果。模型根据这个结果继续推理和行动。

## 9.2 ReAct如何实现

几乎主流的框架，比如DeepSeekHarness，ClaudeCode，OpenClaw，他们的Agent内核都是用的ReAct。面试最常考的是它是如何实现的。先看看这个图，理解它的流程：

**ReAct / Agentic Loop 的基本流程**：

1. 接收用户 Prompt、系统指令、对话历史和工具定义。
2. 模型分析上下文，生成普通文本回复或结构化的工具调用请求。
3. 如果存在工具调用，Harness 执行工具并收集真实结果。
4. 将工具结果回注到对话历史，交给模型继续推理。
5. 如果没有工具调用，普通文本就是最终结果；如果任务尚未完成，则继续循环。

其中核心思路：

1． 提示词告诉AI，让他思考下一步做什么，任务做完没有，要不要调用工具。

2． 外部写一个Harness循环，处理模型吐出的结果。如果模型认为没做完，要调用工具，那么就调用工具（这对应ReAct概念里Act)。如果模型认为做完了，流程结束。

3． 外部调用工具后，将结果返回给模型（这对应ReAct概念的Observation），模型继续思考：下一步做什么，任务做完了吗(对应ReAct里面的Reasoning），进入循环。
```text
while（任务未结束）{
    模型回答 = 调用模型（用户问题 + 对话历史 + 工具列表）
    if（模型要求调用工具）{
        工具结果 = 框架执行工具()
        将工具结果加入对话历史
        continue
    }
    // 没有工具调用，普通文本就是最终答案结束流程
}
```

### 9.3.1 ReAct的核心思想是什么？他是如何实现的？

？思路：这个问题问的很具体了，如果面试官直接问，你介绍一下什么是React，也可以按这个提问的思路介绍（是什么，如何实现的。
答题思路是先把ReAct的概念讲清楚就好了，Resoning和Act，分别是什么，概念讲清楚。（答案中第一段）然后我这里补了一个工程上的实现（答案中第二段），以开源框架DSH为例，具体举例，引经据典，把话题引到你熟悉的框架上。当然你也可以替换成你熟悉的其他框架。
答案：ReAct是Reasoning，也就是推理，和Acting，也就是行动的结合。它的核心思想是让Agent把推理和行动交替进行：模型先判断下一步应该做什么，再通过工具采取行动，然后根据行动结果继续判断，而不是只依靠模型内部知识一次性生成答案。
这里的Reason主要包含两部分：一部分是规划，也就是分析当前任务、判断下一步应该做什么；另一部分是反思，也就是拿到工具执行结果以后，判断结果是否有效、任务是否已经完成，以及是否需要调整原来的计划。
Act是采取行动。在现在的Agent系统中，通常表现为模型选择一个工具，并生成对应的调用参数。比如模型发现缺少实时信息，就可以调用搜索工具；需要验证代码，就可以调用代码执行工具。工具执行后，外部框架会把真实结果返回给模型。
在工程实现上，外部框架会把用户问题、历史消息和可用工具交给模型。模型如果认为需要调用工具，就返回结构化的tool-call；框架负责执行工具，并把执行结果加入对话历史，再次调用模型。如果模型认为信息已经足够，就不再调用工具，而是直接返回普通文本答案，这时框架结束流程。
比如DSH的ReactLoopAgent就是这样实现的：模型负责推理、选择工具以及判断任务是否完成，外部框架负责执行工具、回传结果和维持整个循环。这样Agent就可以在执行过程中根据真实结果不断调整，而不是从一开始
