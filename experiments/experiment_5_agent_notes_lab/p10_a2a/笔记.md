## 形状

### 一、协议本体就是一张表

```python
ALLOWED_TRANSITIONS: dict[str, set[str]] = {
    SUBMITTED:       {WORKING, REJECTED, CANCELED, AUTH_REQUIRED},
    WORKING:         {INPUT_REQUIRED, AUTH_REQUIRED, COMPLETED, FAILED, CANCELED},
    INPUT_REQUIRED:  {WORKING, FAILED, CANCELED},        # ★ 双向的这一格
    AUTH_REQUIRED:   {WORKING, FAILED, CANCELED},
    COMPLETED:       set(),                              # 终态：出不去
    CANCELED:        set(),
    FAILED:          set(),
    REJECTED:        set(),
}

def transition(self, new_state, message=None) -> None:
    if not self.can_transition_to(new_state):
        raise StateTransitionError(self.id, self.status.state, new_state)
        # ★ 非法迁移是**异常**，不是返回值
    self.status = TaskStatus(state=new_state, ...)
```

**这张表就是 A2A 和「一次 RPC 调用」的本质分界。** MCP 的成功/失败是两格，
这里是八格，而且有一格（`INPUT_REQUIRED`）**在 MCP 里根本没有对应物**。

### 二、客户端：A2A 比 MCP 多出来的那个循环

```python
def send_task(self, card, text, *, idempotent=False) -> Task:
    return agent.send_task(message, idempotent=idempotent)     # 派发，立刻返回，不等它干完

def wait(self, task, *, max_steps=12) -> WaitResult:           # ★ MCP 里没有这一步
    for _ in range(max_steps):
        if task.state in TERMINAL_STATES:
            break
        if task.state == INPUT_REQUIRED:
            return WaitResult(task, updates, "needs_input")    # ★ 停下来，把控制权交还
        agent.step(task.id)
        ...
    return WaitResult(task, updates, reason)

def run_task(self, card, text, *, on_input_required=None) -> WaitResult:
    task = self.send_task(card, text)
    result = self.wait(task)
    updates = list(result.updates)                             # ★ 进度必须累积
    while result.needs_input and on_input_required is not None:
        self.send_message(task, on_input_required(task))       # 补充输入，任务接着跑
        result = self.wait(task)
        updates.extend(result.updates)                         # 每轮 wait 都是新开一轮
    result.updates = updates
    return result
```

### 三、两个 Agent 的对照（「内部实现不透明」的证据）

```python
class TravelAgent:                              # 分五步，中途会停下来问
    def step(self, task_id):
        action = plan.pop(0)
        handler = {"查订单": self._lookup_order,     # ← 内部通过 MCP 调工具
                   "问偏好": self._ask_preference,   # ← 这里 transition(INPUT_REQUIRED)
                   ...}[action]

class ExpenseAgent:                             # 一步干完，从不提问
    def step(self, task_id):
        task.transition(WORKING)
        task.artifacts.append(...)
        task.transition(COMPLETED)
```

**两者内部毫无共同点，但对外的卡片一模一样。** 换掉整个 Agent，Host 一行不用改。

### 理论 → 代码 对照

| 笔记第 8 章的说法 | 代码里的真实形状 | 反直觉 / 容易漏掉 |
|---|---|---|
| 互操作性（JSON-RPC / HTTP / SSE） | 和 MCP 一样是一次 `_call` | 但**返回的是 `task_id`，不是结果** |
| Agent 卡片（能力/接口/身份/安全策略） | `AgentCard` + `AgentDirectory.route()` | `route()` 返回**列表**，不是单个 |
| 长时协作与异步交互（多轮对话/任务委派/进度更新） | `wait()` + `send_message()` 的组合 | MCP 一行拿到结果，**A2A 要写一个循环** |
| 内部实现不透明 | 两个 Agent 内部完全不同 | 卡片却能长得一样——这正是它的价值 |
| 消息去重 | `send_task(..., idempotent=True)` 按 `messageId` 去重 | 幂等是**协议层**要求，两个内部完全不同的 Agent 都得实现 |

### 最反直觉的三个点

**① `INPUT_REQUIRED` 是 MCP 里没有对应物的那一格**

它意味着：任务可以**停在中间**，等一句话再接着跑（**不是重头来**）。

工具不会在中途停下来问你一个问题——所以 `tools/call` 里**没有这个状态可用**。
这也是为什么 A2A 的客户端必须写 `wait()` 那个循环，而 MCP 客户端只需要一行。

**② 非法迁移是异常，不是返回值** —— `protocol.py:245-248`

`transition()` 在非法时 `raise StateTransitionError`，而且**错误信息里带上
「允许的下一个状态」**（`protocol.py:106-112`）——和 p02 的 `failed_fields`、
p06 的 `availableTools` 是同一个原则：**错误要说下一步该怎么办。**

演示 6 里「终态拦住了再推一下」就是这一行在起作用。

**③ 进度事件必须**累积**，因为每次 `wait()` 都是新开一轮** —— `client.py:203-211`

```python
updates = list(result.updates)          # ★ 第一次的进度先存下来
while result.needs_input ...:
    result = self.wait(task)            # ← 这一次的返回值里**只有这一轮的进度**
    updates.extend(result.updates)      # ★ 不 extend 就丢了前面的
```

**「进度」恰恰是 A2A 相对 MCP 多出来的东西**——丢了它，这个演示就没意义了。

# 8. A2A

（根据最新面试情况，A2A协议的概念，A2A考的没有MCP那么多，没有那么热，但是还是偶尔会问到。暂时问的不深，我们先记一下概念）A2A（Agent-to-Agent）协议的核心目标是让不同智能体之间能够互操作和协作，即使它们来自不同厂商、框架或运行环境。下面是一个简洁介绍：A2A协议的关键特点

1． 互操作性
。通过标准化的消息格式和通信机制，让不同Agent可以发现彼此并交换任务或信息。
。常用技术：JSON-RPC、HTTP、SSE等。

2. Agent卡片（描述元数据）
。每个Agent通过"卡片"描述自己的能力、接口、身份和安全策略，方便其他Agent发现和调用。

3． 长时协作与异步交互
。支持多轮对话、任务委派、进度更新、流式响应，适合复杂场景（如旅行规划、企业流程自动化）。

4. 内部实现不透明
。调用方只知道对方是一个Agent，不关心它内部用什么模型或工具，保证封装性。
适用场景

·跨团队或跨厂商的Agent协作：例如客服Agent与账单Agent协作处理用户请求。
）复杂任务编排：多个专长Agent分工完成一个大任务（如行程规划、供应链优化）。
）生态互通：构建开放的Agent网络，而不是单一厂商闭环。
