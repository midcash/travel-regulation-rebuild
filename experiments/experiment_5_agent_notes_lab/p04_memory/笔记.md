## 形状

**短期记忆 = 装不下就自己压缩的消息列表；长期记忆 = 环境外的文件 + 按需检索。**

### 一、压缩：把较早的历史换成摘要，最近一段留原文

```python
class ContextWindow:
    def needs_compaction(self) -> bool:
        return self.usage() >= 0.8                    # 接近上限就压，不是爆了才压

    def compact(self) -> CompactionResult | None:
        system, history = self.messages[0], self.messages[1:]
        head, tail = self._split(history)
        if not head:
            return None                               # 只剩一条历史消息 —— 确实没得压

        summary = self.summarizer.summarize(head, carry=self._last_summary)  # ★ 显式交接（见第①点）
        self.messages = [system,
                         {"role": "system", "content": summary.render()},   # ★ 摘要是 system
                         *tail]
        self._last_summary = summary
        # 压完还在窗口之上？如实报出来 —— 压缩是尽力而为，不是硬保护

    def _split(self, history):
        tail, used = [], 0
        for message in reversed(history):             # 从后往前收
            if (len(tail) >= self.keep_recent_messages
                    and used + cost > self.keep_recent_tokens):
                break                                 # ★ AND：条数先满足，token 阈值才生效
            tail.append(message)
        if tail and len(tail) == len(history):
            tail = tail[1:]                           # ★ 保留段不能把历史吃光（见第③点）
        return history[: len(history) - len(tail)], list(reversed(tail))
```

class Summarizer:
    def summarize(self, messages, carry=None):
        summary = StructuredSummary()
        if carry is not None:            # ★ 上一次的摘要作为种子进来，不指望它被重新认出来
            summary.decisions = list(carry.decisions)
            summary.key_identifiers = list(carry.key_identifiers)
            ...
        ...                              # 再扫这一批消息
        summary.cap()                    # ★ 决策/待办留最新，标识符留最早

    def _summarize_chunk(self, chunk, summary):
        # 任务状态
        if role == "user" and text:                              # ← 只认 user
            summary.goal = summary.goal or _clip(text, 50)
        for sentence in _sentences(text):
            if any(m in lowered for m in TODO_MARKERS):          # ← TODO：不限角色
                summary.todos.append(_clip(sentence, 50))
            elif role in {"assistant", "tool"} and any(          # ← 决策：只认 assistant/tool
                m in sentence for m in DECISION_MARKERS
            ):
                summary.decisions.append(_clip(sentence, 50))
        for label, pattern in IDENTIFIER_PATTERNS:               # ← 标识符：全角色扫
            summary.key_identifiers += [f"{label} {v}" for v in re.findall(pattern, text)]
```

class HybridRetriever:
    vector_weight, bm25_weight = 0.7, 0.3

    def search(self, query, top_k=3):
        b = _normalize(self.bm25.search(query))
        v = _normalize(self.vector.search(query))
        # ★ 权重只在"这一路真的有结果"之间分配（加权平均），不是死板的 0.7/0.3
        active = (0.7 if v else 0) + (0.3 if b else 0)
        hybrid = (self.vector_weight * v + self.bm25_weight * b) / active

def _normalize(scores):
    if not scores:
        return {}                                   # 零命中：这一路不参与
    top = max(scores.values())
    return {k: value / top for k, value in scores.items()}   # ★ 第 1 名恒为 1.0
```

### 理论 → 代码 对照

| 笔记第 5 章的说法 | 代码里的真实形状 | 反直觉 / 容易漏掉 |
|---|---|---|
| 接近窗口上限时压缩，最近约 N token 原样保留 | `usage() >= 0.8`；`_split` 的两个条件**都**满足才停 | 保留段的**第一约束是条数**，token 阈值只在条数够了之后才生效 |
| 分块生成结构化摘要 | `summarize()` 内部按 `chunk_size` 分块，再 `_dedupe` + `cap()` | 压缩的最小单位是**整条消息**，消息不会被切开 |
| 摘要中**强制保留**四类信息 | `goal` / `decisions` / `todos` / `key_identifiers` 四个字段 | 「强制」= 六条正则 + 两个关键词元组，**不是理解** |
| 摘要必须比原文短 | `cap()` 只做条数截断（`MAX_DECISIONS=4` …） | `cap()` 管条数**不管 token**；`compact()` 没有任何 before/after 比较或回滚 |
| 长期记忆存在运行环境之外（数据库/知识图谱/向量库） | 就是两个 Markdown 文件 | 代码层面**没有任何「不许改」的约束** |
| 按需检索，而不是把全部记忆塞进去 | `as_tool()` 包成 `memory_search`；检索是懒加载的 | 「检索不到」被建模成**工具失败**（且 `retryable=False`），不是返回空列表 |
| 向量 + BM25 按 7:3 混合排序 | 先各自 `_normalize`，再按权重**平均**（权重只在有结果的那几路之间分） | 归一化是「除以最大值」，见第③点 |

### 最反直觉的三个点

**① 四类信息的「存活规则」各不相同——同一个摘要里，决策差点死掉，标识符永生**

| 字段 | 抽取时的角色门槛 | 只靠文本重扫的后果 |
|---|---|---|
| `goal` | 只认 `role == "user"` | 摘要的 role 是 system，**捞不回来** → 靠 carry |
| `decisions` | 只认 `role in {"assistant", "tool"}` | 摘要的 role 是 system，**整批消失** → 靠 carry |
| `todos` | **不限角色** | 能被再扫一遍捞回（但会重复，靠 `_dedupe`） |
| `key_identifiers` | **全角色扫** | **永生** |

关键在于摘要被插成 `{"role": "system"}`。
**它下一轮会作为 `history` 的开头再次进入 `summarize()`**——
但它的 role 是 `system`，不满足决策分支的 `role in {"assistant", "tool"}`，于是：

> 第 1 次压缩记下的决策，在第 2 次压缩后**消失**；
> 而「关键标识符（不可丢失）：…」那一行被 `IDENTIFIER_PATTERNS` **再扫一遍**，
> 经过 10 轮压缩仍能捞回最初的订单号。

**同一个摘要里，一个丢了、一个活着，原因只是两行代码的角色判断不同。**

修法是**显式交接**，而不是指望摘要能从自己的文本里被重新认出来：

```python
summary = self.summarizer.summarize(head, carry=self._last_summary)
```

配套还要改 `cap()` 的取舍方向 —— 这是个连锁反应：

- 决策/待办 **留最新**的：它们描述"现在该做什么"，陈年决策留在摘要里
  只会挤掉新决策的位置。
- 标识符 **留最早**的：订单号、车次是任务对象本身，最早那批往往就是根本，
  而且丢了就再也捞不回来。

一律留最早的话，carry 一来就会变成「第一批决策永生，后面的永远进不来」——
**修好一个洞的时候，很容易在旁边凿出另一个。**

**② `compact()` 有一条静默失效路径——窗口可以涨到 220% 而不压**

`_split` 的停手条件是 **`and`**（条数先满足，token 阈值才生效）。
历史比 `keep_recent_messages` 还短的时候，循环一次都不会 break，
`tail` 把整段历史全收走，`head` 就空了，`compact()` 静默返回 `None`。

> 实测：默认参数下 4 条各约 870 token 的消息，`usage()` 已经是 **2.33**、
> `needs_compaction()` 返回 True，`compact()` **依然返回 `None`**。
>
> 表现是：`usage()` 一路涨、`needs_compaction()` 一直说"该压了"，
> 而压缩一次都没发生 —— **窗口看起来有保护，其实没有。**

配置本身也值得看一眼：4 条各 870 token，**光是"留住最近 4 条"就已经超出
1500 的窗口上限了**。「留住最近 N 条」和「留在窗口以内」在这个配置下
没法同时成立 —— 这才是那条静默路径会出现的根本原因。

修法是保证**每一步都有进展**（宁可少留一条原文），并且把"压完还在窗口之上"
如实报出来（`over_budget_after`）：

> **压缩是「尽力而为」，不是窗口的硬保护。**
> 既然不是硬保护，就不能让调用方以为"压过了就安全了"。

**③ 混合检索的权重是「每路第一名的配额」，而且某一路零命中时那一份权重会消失**

```python
return {k: value / top for k, value in scores.items()}   # 除以最大值
```

第一个后果：**每路第 1 名恒为 1.0**。BM25 的「命中 1 条、分数很高」和向量的
「命中 4 条、全是 0.01 量级噪声」归一化后顶部都是 1.0，
**绝对分数信息被抹平**，只剩相对比例。

> 实测数字：同一个查询里 BM25 原始分 **11.01**、向量原始分 **0.604**，
> 差了将近 20 倍；归一化之后两路的第一名都是 **1.000**。
> 这就是为什么两路**不能共用一个分母** —— BM25 无上界、余弦在 [0,1]，
> 共用分母会让 BM25 单方面压倒那 0.3 的权重。
> `SearchHit` 里同时留了原始分，就是为了让被抹掉的东西还能被看见。

第二个后果：`if not scores: return {}` —— **某一路零命中时，那 0.3 的权重
不是「贡献 0」而是从公式里整体消失**。语义那一路兜回来的文档，
天花板因此只有 `vector_weight` = 0.7，而且同一个文档的分数会随
「另一路这次有没有命中」跳变，跨查询根本没法比。

> 理论说「两路互补、一路漏了另一路兜底」。
> 原来代码里的兜底是**带折扣的**，折扣多大还随查询变 ——
> 那等于把「兜底」悄悄变成了「降级」。

修法是**加权平均**：权重只在"这一路真的有结果"之间分配。
`active = (有向量? 0.7 : 0) + (有 BM25? 0.3 : 0)`，融合分再除以 `active`。
demo 4 里查询 1（BM25 零命中）的融合分从 0.700 变成 **1.000** ——
"另一路没结果"就只是"这一路独自决定排序"，而不是"分数被打七折"。

# 5. Agent的记忆功能

（属干必考内容，熟练掌握《Agenticdesignpattern》第八章有对这一问题专门讲解。我把这个经典面试问题，结合了理论知识和现在最火的OpenClaw结合，我相信这个回答会更让面试官眼前一亮。然后你这么回答其实把话题引到了OpenClaw，所以OpenClaw的知识要好好看，接着面试主动权就在我们手里了！）Agent的记忆功能通常分为短期记忆和长期记忆。
短期记忆通常存在于上下文窗口，包含最近的对话消息，智能体回复，工具调用结果，以及当前交互的反思内容。
但是上下文窗口的容量有限，所以当多轮对话时，我们可以通过总结旧对话片段、强调关键细节等技术来维护这个上下文窗口。以OpenClaw为例，它的Compaction机制就是一个典型实现：当上下文token接近模型窗口上限时，系统会把最近约20，000tokens的消息原样保留，更早的l日消息则用LLM分块生成结构化摘要来替代，摘要中会强制保留任务状态、决策理由、TODO和关键标识符等信息，压缩后上下文变为"摘要加上最近原文"的结构，这样既释放了空间又尽量减少了信息损失。
当会话结束，短期记忆会丢失，所以我们通常也会让Agent支持长期记忆。我们通常使用一个知识库，存储智能体在各种交互场景、任务执行过程中需要长时间保存的信息。数据通常存在智能体运行环境之外，比如数据库，知识图谱，或者向量数据库中。当智能体需要使用长期记忆时，会查询外部存储，检索相关信息和数据并整合到上下文窗口中然后进行使用。还是以OpenClaw为例，它的长期记忆就是工作空间里的Markdown文件一一MEMORY.md存策展过的持久知识和偏好，memory/YYYY-MM-DD.md按日期存追加式日志。在检索侧，系统会对这些文件建立混合搜索索引，同时使用向量语义搜索和BM25关键词搜索，按7：3权重做混合排序。Agent需要回忆历史时，通过memory_search工具按需检索相关片段再拉进上下文，而不是把全部记忆都塞进去，这就是典型的RAG式长期记忆方案。
此外还有一个值得一提的设计，就是短期记忆向长期记忆的自动沉淀机制。OpenClaw在压缩前会静默触发一轮agent回合，提醒模型把当前对话中重要的信息写入记忆文件，这样短期记忆中真正有价值的内容能在被压缩丢弃之前沉淀为长期记忆，保证了记忆的连续性。

### 5.4.1 请介绍一下Agent记忆的常见类型与作用。

思路：这个就是最典型的八股问题了。大的分类上来说，Agent记忆分长期记忆和短期记忆，我参考了一些书籍，再把长期记忆分成：语义记忆，情景记忆，程序性记忆三类，方便大家理解。答题的的时候从这个角度出发，分类型讲解。同时我在长期记忆这里加入了举例，以最近比较火的DSH框架为例，写了例如DSXXX，让答案更具答案：Agent的记忆从生命周期上主要分为短期记忆和长期记忆。其中，长期记忆还可以根据信息内容进一步分为语义记忆、情景记忆和程序性记忆。
短期记忆也叫工作记忆，主要保存当前对话历史、任务目标、最近的工具调用结果以及执行过程中的中间状态。它的作用是保持当前任务的上下文连续性，支持Agent进行多轮对话和多步推理。例如在DSH中，用户消息、模型回复、工具调用和工具执行结果都会记录在当前Session中，并用于构造模型下一轮看到的上下文。当对话过长时，DSH会通过Compa时，DSH会通过Compaction将较早的历史压缩成摘要，从而控制上下文长度。
长期记忆用于跨任务、跨会话地保存信息，可以进一步分为三类：第一类是语义记忆，保存相对稳定的事实、概念和用户偏好，主要用于事实召回和个性化。例如，DSH可以通过MemoryMCP接入外部记忆系统，保存"用户习惯使用TypeScript"用户希望使用中文回答"等信息，并在新的会话中重新检索和使用。
第二类是情景记忆，保存过去发生的事件、对话和任务经历，主要用于回顾历史经验和避免重复犯错。例如，DSH可以通过JSONL或SQLite持久化过去的Session，其中包括对话内容、修改过的文件、调用过的工具以及执行结果。后续可以通过会话查询能力，查找”上一次修复登录问题时采用了什么方案、测试是否通过"。
第三类是程序性记忆，保存完成任务的方法、操作步骤和执行策略，主要用于复用已经形成的技能和工作流程，提高执行效率与稳定性。例如，DSH通过Skill、AGENTS.md和Workflow保存"修改代码前先读取仓库规范"修改完成后运行对应测试"遇到特定任务时加载相应SkillI"等执行规则。从功能上看，这些规则承担了程序性记忆的作用。
总结来说，短期记忆保存Agent当前正在做什么；语义记忆保存它知道什么；情景记忆保存它经历过什么；程序性记忆保存它应该怎么做。
需要注意的是，DSH的跨会话语义记忆需要额外启用MemoryMCP，并不是默认内置开启的。

### 5.4.2 多轮对话状态管理要考虑哪些关键要素

？思路：多轮对话管理，其实就是说短期记忆。问题翻译过来就是短期记忆要考虑什么因素。这倒是一个很好的问题，我们设计Agent的时候，也不妨从这些角度想想，弄清楚这个问题，有帮助于我们把Agent产品想的比较彻底，把技术角度考虑全面。
答案：第一是保存什么。除了必要的对话历史，还要保存当前任务目标、用户已经确认的关键信息和约束、任务执行进度，以及最近的工具调用和执行结果。这样Agent才能理解上下文，并知道当前任务进行到了哪一步。
第二是如何更新。用户可能在后续对话中补充或修改需求，例如把预算从5000元改成3000元。外部框架需要提取这些变化，更新结构化的会话状态。对于明确修改，可以使用新值覆盖旧值；如果信息存在歧义，则让Agent向用户确认。因此，状态管理不能只是不断追加历史消息，还需要外部框架进行提取、更新和校验。
第三是如何控制上下文长度。对话轮数增加后，不能把所有历史无限加入模型上下文。通常可以保留最近的消息，把较早的对话压缩成摘要，同时单独保留任务目标、关键约束和未完成事项，从而兼顾信息完整性、Token成本和响应速度。
第四是如何隔离和恢复。系统需要通过用户ID、SessionID或任务ID隔离不同会话，避免不同用户或不同任务之间发生状态串扰。同时，会话状态最好能够持久化，以便服务中断或工具调用失败后继续恢复任务。
第五是何时清理。会话结束或超时后，短期状态应该被清理或归档。只有稳定、以后仍有复用价值，并且允许长期保存的信息，才需要提炼后写入长期记忆。
理或沉淀为长期记忆。它不是简单地追加上下文，而是由外部框架维护一份准确、精简并且可恢复的当前会话状态。
