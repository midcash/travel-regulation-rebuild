# p04 Agent 的记忆功能

**对应笔记**：第 5 章（+ 11.3 OpenClaw / 12.3 Hermes 的记忆系统细节）

## 记忆分两层

```
短期记忆 = 上下文窗口（最近的对话、回复、工具结果、反思）
           窗口有限 -> Compaction 压成「结构化摘要 + 最近原文」

长期记忆 = 存在运行环境之外的存储
           需要时用 memory_search 工具「按需检索」，而不是全塞进上下文
```

## 演示

| 演示 | 看到了什么 |

| 2 Compaction | 590 → 493 token，压掉 11 条消息，保留 5 条原文 |

| 4 混合检索 | BM25 vs 向量 vs 7:3 融合，含**归一化前后的原始分**对照 |

## 四个关键点

### 1. 摘要必须强制保留四类信息（演示 2）

> 摘要中会强制保留**任务状态、决策理由、TODO 和关键标识符**。

看演示 2 的输出：订单号 `T20260920-0001`、车次 `G102`、日期 `2026-09-21`、
金额 `553 元` 全在摘要里。

为什么是"强制"而不是"尽量"？因为**摘要如果把订单号吃掉了，后面所有工具调用都没法执行**。
这不是信息损失，是任务直接断掉。

### 2. 压缩的核心指标是"必须比原文短"（演示 2）

这个原型第一版就踩了坑：摘要把每条用户消息都抄了一遍，结果压缩后
**反而变大了**。修法是给每一类信息设上限，超了折叠成"N 条已省略"
（`StructuredSummary.cap()`）—— 压缩不是免费的，只是划算。

### 3. 四类信息的"存活规则"不一样，而且这件事会连锁（演示 2 续二）

摘要会被插回消息列表（`role="system"`），下一轮压缩时**又经过同一个抽取函数**。
于是同一份摘要里：

| 字段 | 抽取时的角色门槛 | 只靠文本重扫的后果 |
|---|---|---|
| `goal` | 只认 `user` | 捞不回来 → 靠 carry |
| `decisions` | 只认 `assistant` / `tool` | **整批消失** → 靠 carry |
| `todos` | 不限角色 | 能被捞回（会重复，靠 `_dedupe`） |
| `key_identifiers` | 全角色扫 | **永生** |

修法是**显式交接**：`summarize(head, carry=self._last_summary)`。
配套还得把 `cap()` 的取舍方向改掉 —— 决策/待办留**最新**的，标识符留**最早**的。
否则 carry 一来就变成"第一批决策永生，后面的永远进不来"。
**修好一个洞的时候，很容易在旁边凿出另一个。**

### 4. 压缩是"尽力而为"，不是窗口的硬保护（演示 2 续三）

`_split` 的停手条件是 **`and`**（条数先满足，token 阈值才生效）。
历史条数不够时，`tail` 会把整段历史全收走、`head` 空掉，`compact()` 静默返回 `None` ——
窗口可以一路涨到 233% 而一次都不压。

现在保证每一步都有进展，并且把"压完还在窗口之上"如实报出来
（`CompactionResult.over_budget_after`）。**既然不是硬保护，就不能让调用方以为压过就安全了。**

### 5. BM25 少而准，向量广而糙（演示 4）

| 查询 | BM25 | 向量 |
|---|---|---|
| `改期怎么操作`（换个说法） | **0 命中** | 3 命中，靠共享的「改」字捞回改签相关记忆 |
| `T20260910-0007`（罕见串） | **1 命中，干净** | 1 命中 |
| `报销发票抬头怎么写` | 1 命中 | 4 命中（多出来的是 0.01 量级的噪声） |

单独用任何一个都会漏。7:3 融合之后，精确项由 BM25 顶住，漏掉的由向量兜底。

演示 4 的表里额外列了**归一化之前的原始分**，用来暴露两件事：

- **归一化会抹掉绝对量级**：同一个查询里 BM25 原始分 11.01、向量只有 0.604，
  差了近 20 倍；但归一化后两路的第一名都是 1.000。
  （这也是两路不能共用一个分母的原因 —— 会单方面压倒那 0.3 的权重。）
- **权重只在"这一路真的有结果"之间分配**：查询 1 里 BM25 零命中，
  融合分是 **1.000** 而不是 0.700 —— 兜底不该是打折的兜底。
  否则同一个文档的分数会随"另一路这次有没有命中"跳变，跨查询根本没法比。

**诚实说明**：这里的"向量"是字符特征替身，不是真 embedding。
它只能靠共享字符做模糊匹配，抓不到完全没有共同字符的同义词
（"座位" ↔ "席别"）。真 embedding 的召回会明显更好 ——
所以真实系统的混合检索效果比这个 demo 更强。

## 文件

| 文件 | 作用 |
|---|---|
| `context_window.py` | 短期记忆 + Compaction（`Summarizer` / `StructuredSummary`） |
| `retrieval.py` | BM25 + 向量 + 7:3 混合检索 |
| `long_term.py` | Markdown 记忆文件 + `memory_search` 工具 |
| `main.py` | 5 个演示 |

## 建议打断点的地方

1. `context_window.py` 的 `head, tail = self._split(history)`
   → 哪段被压、哪段留原文，压缩策略就在这几行（含"不能把历史吃光"那道保护）
2. `context_window.py` 的 `for label, pattern in IDENTIFIER_PATTERNS:`
   → 关键标识符是怎么被一条条捞住的
3. `context_window.py` 的 `summarize(messages, carry=...)`
   → 四类信息跨压缩存活的交接点；对照下一个断点看它为什么必须显式
4. `context_window.py` 的 `summary.cap()`
   → 决策留最新、标识符留最早 —— 两类信息的取舍方向相反
5. `retrieval.py` 的 `hybrid=weighted / active if active else 0.0`
   → 7:3 融合的那一行，以及"权重只在有结果的路之间分配"
6. `long_term.py` 的 `remember()`
   → 策展文件和追加日志走的是两条完全不同的路

## 记忆类型对照（笔记 5.4.1）

| 类型 | 存什么 | 存在哪 |
|---|---|---|
| 情景记忆 | 什么时候发生了什么 | `memory/YYYY-MM-DD.md`（追加） |
| 语义记忆 | 事实和知识 | `MEMORY.md`（策展） |
| 程序记忆 | 怎么做一件事、有什么规矩 | `MEMORY.md`（策展） |
| 短期记忆 | 当前这轮对话的上下文 | 上下文窗口（会压缩） |

## 怎么跑

```
python experiments/experiment_5_agent_notes_lab/p04_memory/main.py
```

跑完可以打开 `p04_memory/workspace/` 看真实写出来的记忆文件。

`production.py` 的 `ProductionMemory` 使用版本化、append-only、fsync JSONL 事件保存记忆，并限制 scope 和文本长度；`ContextAssembler` 按 token 预算装配上下文。多副本服务应把这个存储边界替换为数据库。
