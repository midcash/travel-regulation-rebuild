# p03 Agent 健壮性设计

**对应笔记**：第 17 章（Agent 健壮性设计）。这一章是笔记里最工程化的一章，
也是面试里被追问最多的一章：

> 英伟达 Agent 一面：Agent 遇到异常故障时，用什么方式保持持续健壮的运行？
> 宇树科技 Agent 一面：外部工具调用失败后，系统如何容错或降级？

## 一句话总纲（笔记原话）

**先分类，能恢复就受控恢复；不能恢复就熔断；确实不可用就优雅降级。**

整体处理思路四步：**错误分类 → 局部恢复 → 故障隔离 → 优雅降级**。

## 五个必须看懂的点

### 1. 分类是分水岭（演示 1 vs 演示 2）

同样是"工具调用失败"：

- **瞬时技术故障**（超时、429、5xx）→ 过一会儿可能自己好 → **可以重试**
- **确定性调用错误**（参数错、权限不足、违反业务规则）→ 重试一百次也一样 → **不要重试**

笔记原话：*不能对所有失败统一重试*。面试时这一句就能把答案和"失败后重试三次"区分开。

### 2. 熔断的目的不是修复工具（演示 3）

> 熔断的目的不是修复工具，而是保护 Agent 和下游系统。

看演示 3 里的 `下游被真实调用的次数`：熔断打开后，第 4 次调用**一次都没打到下游**。
这就是熔断和重试的区别 —— 重试是在冲击下游，熔断是在停止冲击。

注意阈值数的是**调用**，不是尝试：要连打 3 次调用（每次内部自己重试 3 次）才熔断。
按尝试记的话，阈值 3 的真实含义会变成"一次调用里重试 3 次"，
熔断器就成了重试次数的复读机。**重试预算和熔断预算是两个预算，各管各的。**

### 3. 降级链是有顺序的（演示 4）

```
备用工具 → 缓存/已有中间结果 → 部分结果（明确缺失项）→ 只读建议 → 转人工 → 明确失败
```

注意演示 4-c：返回部分结果时**必须明确缺失项**，不能悄悄少给。

### 4. 权限必须跟着能力降（演示 6）

> 启用备用模型不等于保持原有权限。

演示 6 里 `backup-mini` 能接管，但它 `complex_reasoning=False`、`rule_following=False`，
所以权限从「自动执行写操作」直接降到「只生成草稿，人工确认后执行」——
查询还能做，退款必须人来点。

### 5. 「超时」是调用方的容忍度，「不降级」不等于「不转人工」

这两件事都属于"名字听起来是一个意思，其实是两个"：

**超时（演示 1-b）**：那个工具**从没抛过异常**，它每次都把结果算出来了，只是花了 8 秒。
超过 `timeout_s=5` 之后结果照样判废 —— **一个迟到 8 秒的正确结果，
和一个失败，对调用方没有区别**。所以它归到瞬时故障（可重试），
而不是确定性错误。推论是"单次超时"和"总预算"必须是两个约束：
每次调用都刚好卡在超时线以内，重试 10 次照样能把任务拖垮。

**降级 vs 转人工（演示 5）**：

| | 做什么 | 代价 |
|---|---|---|
| 降级 | 换一个更弱的能力顶上，任务**继续** | 数据可能不对 |
| 转人工 | 承认自动路径做不了，把决定权**交回人** | 慢，要有人接 |

高风险写操作最不能接受的恰恰是**悄悄失败** —— 用户的钱卡在半路，必须有人接手。
所以 `allow_degradation=False` 只该关掉降级阶梯，不该把转人工也关掉。
演示 5 的 5-a / 5-b 就是这个对照。

## 建议打断点的地方

1. `resilience.py` 的 `category, reason = classify(result)`
   → **整个文件最重要的一个判断**：这次失败该不该重试
2. `resilience.py` 的 `allowed, why = self.breaker.allow(self.clock)`
   → 熔断状态机；注意它在"打网络之前"，和 `settle()` 一起看粒度
3. `resilience.py` 的 `if result.ok and elapsed > self.retry.timeout_s:`
   → 单次响应超时：迟到 = 失败
4. `resilience.py` 的 `_degrade_or_fail(...)` 里的 `ladder = [] if not allow_degradation`
   → "不允许降级"只关阶梯，转人工照走
5. `model_gateway.py` 的 `permission = downgrade(permission, 1)`
   → 权限怎么跟着能力降


## 关于时间

时间是可注入的（`VirtualClock`）：退避、冷却、半开探测全部瞬间走完，
但每一步"**本来要等多久**"都打印出来了。所以调试时不用真的等 8 秒，
而且每次运行结果完全一致。
