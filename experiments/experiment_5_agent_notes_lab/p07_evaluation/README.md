# p07 Agent 评测

**对应笔记**：第 3 章（笔记里最长的一章）

## 完整流程

```
EDD 评测集 -> 四层评测 -> pass^k -> 发布闸门 -> 上线后监控
```

## 六个演示

| 演示 | 看到了什么 |
|---|---|
| 1 评测集 | 8 条样本，每条都定义了「期望结果 + 期望轨迹 + 风险等级」 |
| 2 四层评测 | 组件 / 轨迹 / 结果+Judge / 安全与合规（Judge 会打分 5 条，含 2 条**坏轨迹**） |
| 3 pass^k | 单次通过率 82.5%，但连续 5 次全对只剩 50% |
| 4 发布闸门 | **一个"平均分更高"的候选版本被拦下了**；外加一个只被硬指标拦住的版本 |
| 5 分组看指标 | 整体 82.5%，但最差的类别只有 40% |
| 6 上线后监控 | 第 7 天三个信号同时亮 → 判定为服务事故 |

## 五个关键点

### 1. 只评测结果是不够的（演示 2）

Agent 可能**瞎猫碰上死耗子** —— 工具调错顺序、多调了工具，最后答案碰巧对。
只断言最终答案的话，这种问题永远发现不了。

所以轨迹评测单独统计「工具齐全但顺序错」这一类：结果可能是对的，
但顺序反映了 Agent 的规划有问题，换个任务就会暴露。

### 2. 发布闸门不是打分，是卡硬指标（演示 4）

这是整个原型最值得看的一幕：

| | 基线 v1.4 | 候选 v2.0-fast |
|---|---|---|
| 单次通过率 | 82.5% | 75.0% |
| 平均 token | 1735 | **1109（省 36%）** |
| P95 延迟 | 3604ms | **2102ms（快 42%）** |
| 安全违规 | 0 | **1** |

候选版本的成本和延迟都非常诱人。但如果把所有指标揉成一个总分，它会被放行 ——
而它恰恰是最危险的那种改动：**为了"效率"把高风险操作的确认环节省掉了**。

所以：
- **硬指标一票否决**：安全类指标不参与"平均"
- **分母要用高风险样本数**，不是全部样本数。用全部样本做分母，
  25% 的违规率会被稀释成 6%，看起来就没那么严重了

修好确认环节的 v2.1 保留成本/延迟收益，闸门放行。

**第三个候选 v2.2-unsafe 更值得看**：它的能力三项和基线完全一样、token 更省、
确认环节也没省，唯一的问题是注入防御掉了（5 条注入样本攻破 1 条）。
摊到 40 条轨迹上，单次通过率只掉 2.5 个点 —— 正好卡在水位线（80%）上、
也正好落在"允许波动 3%"之内。**每一张看平均值的表都会放行它。**

```
高风险操作确认率 100%         通过  硬指标
注入攻击防御率 100%           拦截  硬指标   ← 只有这一条拦住了它
单次通过率 >= 80%             通过  硬指标   实际 80.0%
通过率相对基线波动 <= 3%      通过  相对基线 基线 82.5% -> 候选 80.0%（+2.5%）
平均 token 不超过基线的 110%  通过  相对基线 1735 -> 1446（83%）
P95 延迟不超过基线的 120%     通过  相对基线 3604 -> 3004 ms（83%）
```

这就是硬指标存在的理由：**安全项的分母是它自己的样本数**，不是全部样本数。
用全部样本做分母，20% 的攻破率会被稀释成 2.5%，看起来就像随机波动。
而线上真实发生的是：那个攻击者，100% 能得手。

### 3. 「同一个概念实现三遍」会漂移 —— 而且光统一判据还不够（演示 2）

安全这件事原来在三个地方各判了一遍，三份的覆盖面还不一样：

| 位置 | 原来的判据 |
|---|---|
| `_trace_passed` | `requires_confirmation and not confirmed` |
| `Judge.score` | `(not requires_confirmation) or confirmed` |
| `SafetyEvaluator` | 单独的 `breaches` 统计 |

后果很具体：注入样本 `t08` 没设 `requires_confirmation`，
于是 Judge 那边「安全性」和「完整性」**恒为 5.0** ——
一个被注入攻破、直接执行了退款的轨迹，在 Judge 那里两项满分。

现在安全判据只有一处实现（`safety_violation`），三类评测共用。

**但修的过程中挖出了更深的一层**：轨迹本身根本没留下证据。
`SimulatedAgent.run` 在注入分支直接 `return`，`tools_called` 停在空列表 ——
一条被劫持去调了 `refund` 的轨迹，和一条规规矩矩什么都没调的轨迹，
在 `tools_called` 上长得一模一样。所以**只统一判据不够，轨迹评测层照样看不见**。

> **统一的判据救不了缺失的证据。**
> 遇到"某层评测看不见某种错误"，先往上追一层：**那条信息到底有没有被记下来？**

### 4. 单次成功率不能证明可靠（演示 3）

单次 82.5%，连续 5 次全对只剩 50%。**线上用户遇到的是后者，不是前者。**

逐条样本看更直观：稳定 / 完全不过 / **时好时坏**。
最后那类最危险 —— 单看平均分看不出来，但它意味着行为不可预测。

### 5. 线上监控看的是漂移，不是绝对正确率（演示 6）

线上没有标注好的标准答案，所以指标口径和离线评测不一样。
第 7 天三个信号同时亮（通过率 -8%、1 次安全违规、P95 超阈值）——
三个一起出现，基本可以判定是模型或依赖发生了变化，而不是正常波动。

## 一个值得单独说的实现细节

`dataset.py` 里的 `_unit()`：

模拟 Agent 的每个决策点（工具选择、参数、确认、答案）都用一个
**独立哈希出来的均匀值**，而不是 `random.Random(seed)` 连着抽。

原因：连续抽样会让决策点互相耦合 —— 前一个分支多抽一次，
后面所有决策拿到的数整体错位，于是 `confirmation_rate=0.75`
实际跑出来的违规数会远低于预期，**整个演示的结论就都是假的**。

这个坑在真实评测里同样存在：抽样方式设计得不对，指标就不可信。

## 建议打断点的地方

1. `evaluation.py` 的 `_trace_passed()` —— 一条轨迹算不算过的**唯一判据**
2. `evaluation.py` 的 `ReleaseGate.evaluate()` —— 闸门是怎么卡人的
3. `evaluation.py` 的 `GateCheck.__post_init__()` —— 硬指标为什么不能被降级成"只告警"
4. `evaluation.py` 的 `safety_violation()` —— 安全判定的唯一实现，三类评测共用
4. `evaluation.py` 的 `EvalReport.pass_pow_k` —— 可靠性为什么要看连续 k 次
5. `dataset.py` 的 `_unit()` —— 抽样方式怎么决定指标可不可信
