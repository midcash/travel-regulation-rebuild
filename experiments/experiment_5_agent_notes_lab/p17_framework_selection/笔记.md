# 第 1 章 · Agent 开发框架与工程实践

> 对应原文：顶层 `07-Agent开发框架与工程实践.md` 第 1 章
> 对应原型：`p17_framework_selection/`

## 形状

```text
共同内核：模型适配 + 工具 + Agent Loop + 状态/记忆
        + 流程控制 + 权限/Trace/评测/可靠性

团队/部署硬约束 → 项目最难问题 → 选择开发形状 → 模型与发布偏好
```

## 知识点总括

- 框架不是 Agent 智能的来源，而是对模型、工具、状态、流程、权限和可靠性的工程封装。
- 需要掌握框架的定位、优点、局限和选型理由，不必脱离项目背 API。
- 六种常见使用方式分别是组件组装、状态图、角色化团队、长任务环境、知识管道和平台化编排。
- LangChain 偏通用组件生态，LangGraph 偏显式状态与恢复，DeepAgents 偏长任务，OpenAI Agents SDK 偏轻量 Agent/Handoff，Claude Agent SDK 偏环境操作，Google ADK 偏完整工程编排，CrewAI 偏角色协作，PydanticAI 偏类型安全，LlamaIndex 偏数据/RAG，Dify 偏低代码发布，AgentScope 偏国内模型/Java/私有化，Microsoft Agent Framework 偏微软企业栈。
- 选型四步：先看团队技术栈和硬约束，再看项目核心问题，再看部署平台，最后看模型偏好；最终通常保留一个主框架和少量候选。
- 不应把 GitHub Stars 当生产成熟度，也不应因为框架热门就强行使用；框架抽象仍不能替代评测、权限、幂等、审计和生产可靠性。

先运行 `main.py`，把每个候选框架的“开发形状”和“适用边界”对回原文。
