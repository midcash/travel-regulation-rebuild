## 三个关键点

### 1. cron 和 loop 的差别只有一行代码（演示 2）

笔记 13.1.2 那句话是整章的分水岭：

> cron 跑的是一段固定脚本，第一步、第二步、第三步，永远一样。
> loop 跑的是一个 agent：它看当前状态，自己选下一步该干啥。
> **一句话，cron 是在执行脚本，loop 是在模仿一个工程师。**

这个原型把它做成了可测量的：同一个任务、同一套工具、同样的轮数预算。

| | 轮数 | 结果 | 停下原因 |
|---|---|---|---|
| cron | 3 | 没修完 | 无进展：连续 2 轮卡住 |
| loop | 4 | 全部通过 | 目标达成 |

cron 每一步都没做错。它跑了 formatter、跑了通用修复、跑了测试，
而且把三个「通用做法能修」的问题全修了。

它唯一没做的事是：**看一眼上一轮发生了什么。**

代码上的差别就是这么一处——`Worker.decide()` 读了状态才决定下一步，
`CronRunner.decide()` 直接返回写死的脚本。**除此之外两个执行者一模一样。**

### 2. 预算是每轮开始前问的，不是事后算账（演示 3）

笔记 13.1.4：**预算就是架构的一部分。**

```
if state.spent_usd + self.cost_per_iteration > self.budget_usd:
    return "预算不够再跑一轮"
```

关键是问的是「**再跑一轮**会不会超」，不是「已经超了没」。
演示 3 的 C 场景花了 $0.30 就停了，一分没超。

改成事后算账的话，它会先把钱花掉，然后告诉你超了。
这个差别在真实系统里很实在：账单总是晚一步，但拦截可以早一步。

### 3. 「多数投票」两头不讨好（演示 6）

笔记 13.2.4 说：

> 20 个使用同一模型、读取同一份错误上下文的 Agent，
> 可能会**以工业化规模彼此赞同**。

这句话可以直接量化。两组审计 Agent，单个人的漏检率都是 35%、
误报率都是 30%、人数都是 3 个——**唯一的差别是模型和上下文是否同源**：

| Reviewer 组 | 汇聚规则 | 漏检率 | 误报固化率 |
|---|---|---|---|
| 同质（同模型同上下文） | 任意一个 | 35.4% | 30.4% |
| 同质（同模型同上下文） | 多数 | 35.4% | 30.4% |
| 同质（同模型同上下文） | 全体一致 | 35.4% | 30.4% |
| 异构（不同模型独立上下文） | 任意一个 | **4.2%** | 65.9% |
| 异构（不同模型独立上下文） | 多数 | 28.3% | 21.8% |
| 异构（不同模型独立上下文） | 全体一致 | 72.8% | **2.7%** |

三件事：

1. **同质组的三行一模一样。** 换成什么规则都没用——三份拷贝还是**一份判断**。
   一个人漏了，三个人一起漏；一个人误报，三个人一起附和。
2. **两个方向要的规则是相反的。** 要召回就用「任意一个」，要精确就用「全体一致」。
   它们不可能同时成立，所以必须先想清楚最怕哪种错。
3. **「多数」在两个方向上都输给某个极端**（28.3% vs 4.2%；21.8% vs 2.7%）。
   它不是一个折中，而是两头不讨好——因为「多数」这个规则本身没有方向，
   它只是在数人头。这正是笔记说「**而非盲从单一多数意见**」的原因。

## 一个从实测里长出来的知识点（演示 1）

loop 跑了 4 轮全绿，但 `review-typehints` 一直没被修，它还是过了。

原因：评审是**打分制**（每个未修问题扣 1 分，5 减 1 等于 4，正好卡在门槛上）。

这就是打分制的特点——**它天然会留一个小尾巴**。所以:

- 关键项要用**通过/失败制**（`lint`、`test` 就是），不能用打分制
- 一个「4 分就能上线」的门槛，等于宣布「可以留一个问题不修」

演示 3 的 A/B 场景一开始就踩了这个坑：`needs_human` 的问题挂在 `review` 上，
结果打分制给了它 1 分的余地，整个演示不成立。改成挂在 `test` 上才对。

## 踩过的两个坑（都留在代码注释里）

1. **状态文件的「坑」匹配不上**（`loop_engine.py` 的 `pitfall_id()`）
   最早写成 `defect.id in known_pitfalls`，而列表里存的是
   「lint-import-order：通用做法修不掉它……」整句，于是永远匹配不上，
   「读状态文件」那一组省下的轮数成了 0。
   **状态文件是给人读的文本，读取方必须知道怎么解析它**——这是用 Markdown 当存储格式要付的代价。

2. **人工否决没有拦住发布**（`graph.py` 的 `Graph.run()`）
   图上确实停在 `human_review` 了，但 `shipped` 还是 `True`（它只看 `test_passed`）。
   一个人工否决会在报表上显示成一次成功发布。
   **「跑完了」和「发布了」必须在代码里分开。**

## 建议打断点的地方

1. `loop_engine.py` 的 `Worker.decide()` —— **loop 和 cron 的全部差别就在这个函数里**
2. `loop_engine.py` 的 `Heartbeat.check()` —— loop 是怎么知道该停的
3. `loop_engine.py` 的 `Loop.run()` —— 一轮循环的完整形状（读记事本 → 决定 → 执行 → 检查 → 写记事本 → 问心跳）
4. `loop_engine.py` 的 `StateFile.save()` —— 记事本到底写了什么进磁盘
5. `graph.py` 的 `Graph.run()` —— 节点返回值怎么决定下一步（旁路、并行、回环都长在这）
6. `graph.py` 的 `tally()` —— 同质组的三个人为什么是「同一双眼睛的三份拷贝」

## 怎么跑

```
python experiments/experiment_5_agent_notes_lab/p08_loop_graph/main.py
```

跑完之后打开 `workspace/demo4-STATE.md` 看看——loop 的公共记忆就是这样一个纯文本文件。
你可以手动改它（比如把「踩过的坑」删掉），再跑一次，观察 loop 重新走一遍试错。

`production.py` 的 `ProductionGraph` 将节点和允许迁移显式化，所有迁移写入 checkpoint JSONL，并有最大步数和终态保护；非法迁移直接失败，不静默修正。
