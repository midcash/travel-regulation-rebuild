## 形状

**整个文件只有两个聚合算子。** 五种架构的差别，就是这两个布尔表达式，
加上各自跑过的路径不同。

```python
def _trial(agent, rng) -> bool:                    # 全文件唯一的错误注入点
    return rng.random() >= agent.error_rate        # 默认 0.25

class Ledger:                                      # ★ 四个指标全部由它数出来
    tokens_per_call: int = 300                     #   唯一允许假设的是**单位成本**
    def reason(self, count=1):                     #   记一层 LLM 调用：
        self.llm_calls += count                    #   count=1 是串行一步；
        self.tokens += count * self.tokens_per_call#   count=N 是 N 个 Agent **并发**一层
        self.depth += 1                            #   所以"深度"不会随人数增长
    def talk(self, count=1): self.messages += count

@dataclass
class Outcome:                                     # 五个 runner 共用的返回契约
    name: str
    correct: bool                                  # 一次运行 = 一个二值裁决
    llm_calls: int; sequential_depth: int; messages: int; tokens: int

# ── 算子 A：连乘 → 放大错误 ──────────────────────────
def run_independent_synthesis(agents, rng):
    results = [_trial(a, rng) for a in agents]
    ledger.reason(len(agents)); ledger.reason(len(agents))   # 两层，每层 N 次并发
    return Outcome(..., correct=all(results), subtask_results=results, **ledger.metrics())

# ── 算子 B：多数决 → 吸收错误 ────────────────────────
def run_independent_vote(agents, rng):
    results = [_trial(a, rng) for a in agents]
    return Outcome(..., correct=sum(results) * 2 > len(results), ...)

# ── 中心化：唯一一行「压制放大」 ──────────────────────
def run_centralized(agents, rng, gate_catch_rate=0.8):
    ok = _trial(agent, rng)
    if not ok and rng.random() < gate_catch_rate:  # 门控只审「第一轮已经错了」的
        ok = _trial(agent, rng)                    # 打回 → 返工一次
    ...
    if rejected: ledger.reason(rejected)           # ★ 返工是**新的一层**
    ledger.reason()                                #   最后：主管汇总
    return Outcome(..., correct=all(results), ...) # ★ 终局仍然是 all()

# ── 跑 4000 次，统计 ────────────────────────────────
def simulate(runner, agents, trials=4000, seed=20260911):
    for _ in range(trials):
        failures += not runner(agents, rng).correct
        depth = max(depth, outcome.sequential_depth)   # ★ 深度取最坏情况，不是最后一次
    return ArchitectureStats(amplification=error_rate / agents[0].error_rate, ...)
```

| runner | 控制流形状 | 聚合 |
|---|---|---|
| `run_sas` | 一次 `_trial` | — |
| `run_independent_synthesis` | 并行 N 个**不同**子任务 | `all()` 连乘 |
| `run_independent_vote` | 并行 N 个**同一**任务 | 多数决 |
| `run_centralized` | 并行 N → 逐个门控返工 | `all()` 连乘 |
| `run_decentralized` | N 个初值 → 若干轮两两互评 | 多数决 |
| `run_hybrid` | 逐个：同伴先救 → 救不回才门控 | `all()` 连乘 |

`AgentContext` 由谁构造、塞进谁的 `messages`：

| 四个协调指标是可量化的 | `Ledger` 逐笔记账，`**ledger.as_metrics()` 交给 `Outcome` | 单位成本是参数，总量是数出来的 —— 两者别混 |

### 最反直觉的两个点

**① 表里四个指标，「数出来的」和「假设出来的」必须分得清**

原来只有 `correct` 是从运行里测的。`llm_calls` / `sequential_depth` / `tokens`
是 runner **手写的常数**：

```python
run_sas:    llm_calls=3, sequential_depth=3, tokens=900     # 直接写死
run_hybrid: sequential_depth=3                               # 硬编码
```

问题不在于"不准"，在于**不会随代码变**：你把流程从 3 步改成 5 步，
那个 3 还老老实实待在那儿，而表格照样印出来，**看起来和真测的一样**。

现在四个指标全部由 `Ledger` 数出来。分工是这样的：

| | 例子 | 性质 |
|---|---|---|
| **单位成本** | `Ledger(tokens_per_call=800)` | 参数，**允许假设**，写在构造函数里谁都能看见 |
| **总量** | `llm_calls=ledger.llm_calls` | 结论，**必须由跑的过程数出来** |

这个 `reason(count=N)` 的设计还顺手把一件事讲清楚了：
**"一层里有 N 次调用"就是并行**。调用次数照加，顺序深度只算一层 ——
这正是"多 Agent 并行"在指标上的样子：算力翻倍，串行长度不变。
**顺序深度不能等于调用次数**，差的就是这个。

改成实测之后，表里立刻有一列动了：**混合架构的顺序深度从 3 变成 4**。
它的返工其实分两层 —— 先"同伴指出的那些"并行重做，再"主管打回的"并行重做，
这两层在时间里是分开的。原来那个常量把它们拍扁成了一步。

> 这也是**实测代替常量**最典型的好处：不是数字变准了，是**结构上的事实浮出来了**。
> 另一处同理：`simulate()` 原来写 `depth = outcome.sequential_depth`，
> 等于让最后一次试验单独决定整张表这一列 —— 现在改成取**最坏情况**，
> 因为深度是结构属性，某一轮恰好没人返工不代表这个架构变浅了。

**② 门控把子任务错误率从 25% 砍到 10%，最终错误率反而从 25% 涨到 27%**

这是全原型最值得看的一处，因为它是一个**反直觉的算术结果**：

```python
if not ok and rng.random() < gate_catch_rate:   # 0.8 是**条件**概率：只对已经错的掷骰
    ok = _trial(agent, rng)                     # 且只重考一次，没有 while
```

单任务错误率因此变成 `p·(0.2 + 0.8p)` = **0.25 → 0.10**（2.5 倍改善）。
但终局是 3 个子任务的 `all()` 连乘：

```
1 − 0.9³ ≈ 0.271        ← 反而比单体 0.25 更差
```

> **门控在子任务层面确实有效，在终局层面被连乘吃光。**
> 这也解释了为什么中心化 1.07× 只比单体 0.99× 略差一点，
> 而不是笔记引的论文数字 4.4×。

## 6.1 典型的Agent架构

（看着就是几种模式，其实你更要想清楚，这几种模式为什么好/不好，使用什么场景，理解复杂度指标，这个需要一些理解成本的，不要以为这个很简单，请大家结合上面资料理解一下，另外这块确实很重要，也值得我们仔细理解）1)SAS（Single-AgentSystem）单体架构

交互类型：一个Agent 顺序地感知→推理/规划→行动→迭代。
复杂度指标：
LLM调用次数：O(T）（T为推理轮次)
顺序深度：T
·通信开销：0
·并行化能力：1
特点：最简单、最稳。当单体基线已经不错（论文里经验阈值~45%），再加协调通常收益递减或为负。顺序型长
链推理（一步错步步错）用单体更安全
适用场景：工具密集型任务、顺序推理任务、单Agent基线性能已经较高的场景。
2）MAS（Independent）独立多体
交互类型：多个Agent独立并行做同一任务，最后做聚合/投票/综合（Synthesis）。
LLM调用次数:O(N·T）+O(1)
）通信开销：1（仅最终聚合）
特点：并行度最高、协调成本最低，但缺少互相纠错的机制；论文发现这种拓扑的错误放大最严重（17.2×），因
为各自错误会在聚合时被"叠加/扩散"。
适用场景：独立样本批处理（如并行评审、并行方案生成），且容错要求不高的场景。若任务需要大量工具或严格
一致性，谨慎使用。

## 6.2 Agent架构设计原则

## 6.4 Agent之间通信和状态管理

（这个知识点不是上面提到的论文中的内容，但是这个点和多Agent相关，有了多Agent同样要知道的它们之间是如何交互的，以及传递什么信息？虽然不算特别高频考点，但是也是被问到过的，需要准备。）常见的Agent的通信模式：

1. Agent间通信有三种常见模式：

·移交（Handoff）：一个Agent将执行上下文和执行权完整传递给另一个Agent，自身退出。控制权转移，就像接力跑把棒交出去。

·工具调用（ToolCall）：一个Agent（主管）将任务委托出去，保留控制权，等结果回来后自己决定下一步，负责最终输出。（ClaudeCode里面的SubAgent的做法）

·消息协作：多个长期驻留Agent持续交换消息并协同推进任务，允许横向通信与并行协作。（ClaudeCode里的AgentTeam的做法）
当 Agent 1 调用 Agent 2 时，需要明确 Agent 2 能看到哪些信息。常见做法是由外部框架构造新的上下文，只传递必要的消息、工具参数和任务产物，而不是默认共享全部内部状态。

移交更适用于自主协作的场景，而工具调用则提供了更明确的层级控制和接口约束。
2. 消息传递内容：Agent与Agent之间应该传递所有的消息还是部分消息，需要根据具体的业务场景权衡。

消息传递可以分为两类：共享完整的中间状态，便于协作但会迅速扩大上下文；只共享最终结果，能控制上下文规模，但需要为每个 Agent 定义清晰的结果模式。实际系统通常还会通过工具调用、内存通道或文件邮箱传递结构化结果。
共享完整推理数据：智能体将其所有中间步骤（如链式思考、工具调用）写入共享通道。相当于提供了一个共享区，用于其他智能体理解其推理过程，可以提升系统的整体协作与推理能力。但是这种方式的缺点是会导致状态空间快速膨胀，给上下文窗口和内存管理带来挑战。
仅共享最终结果：智能体在私有空间内完成其计算，仅将最终结果写入到共享区。它能有效控制状态的复杂度，实现此策略需要为每个智能体定义独立的状态模式。
3. 通信介质（怎么传）

SubAgent的做法）

### 6.5.1 动态网络浏览问题

(此例子截取自论文）问题描述：我们需要通过网络搜索，找到某公司2024年可持续发展报告中关于碳排放的问题，请你针对这个问题设计一个Agent架构。
架构设计：因为网页导航是高熵，路径不唯一的场景。不同的来源（官网，媒体，报告）可以被并行搜索更快覆盖。
在这种场景下，我会使用去中心化架构设计整个系统，使用去中心化架构既能够提升并行速度，可以减少中心调度的串行瓶颈。
具体来讲，整个系统各个Agent是平级的，他们自主并行探索。系统里面使用事件总线/共享黑板的方式，所有Agent订阅相关话题，他们可以发布任务，认领任务，提供帮助，提交答案，来实现点对点的协作。
具体来讲，系统里有：任务规划Agent，将用户目标拆分成子任务后，发布任务。
然后官网探索Agent，媒体报告等Agent认领任务后，各自探索，调用工具汇总任务，直到达到标准然后会提交任务，交给验收Agent验收。
验收Agent验证通过后，交付对发布停止信息，终止验收Agent验证通过后，交付给汇总机器人汇总信息，如果汇总Agent认为目标达成，及时发布停止信息，终止流程进行交付。

### 6.5.2 金融推理任务

任务描述：任务描述：设计一个分析某个上市公司的估值的Agent。
架构设计：金融估值的流程通常比较规范，天然具有分而治之的特点，多个子问题之间相对独立，可以并行。
具体来讲：我会先设计一个主管Agent，他将任务分解成多个阶段，设计并行窗口，验收，将任务下发给子Agent去并行完成。
主管Agent下设置多个子Agent，比如收集官网信息Agent，收集市场监管信息Agent，收集友商信息做对比的Agent.整个过程由主管Agent负责验收，当Orchestrator验收通过，下发停止信号中止整个流程并交付。

### 6.5.4 时空冲突检测任务

（选自真题：夸克千问架构设计题目，我就准备直接套用6.5.2的模板）任务描述：设计一个Agent系统，让它完成当用户创建一个行程后，判断这个行程是否和其它冲突，如果有冲突，给出重新规划的建议。
架构设计：行程冲突检测和规划本质是约束满足+顺序调整，流程比较规范，需要考虑时间窗口，地点，偏Orchestrator统一拆解，分派和收敛，降低并发协作带来的协调成本和不一致风险，确保各步骤按既定顺序执行也能够并发。
具体来讲：我会先设计一个Agent作为总指挥，根据当前阶段来分配下发任务，控制并发窗口，验收，和控制中止。
然后我会设计多个子Agent。比如行程Agent：负责整理相关的行程，和行程时间相关的数据。地点Agent：评估各个行程地点相关Agent的通行时间等，冲突检测Agent，用户喜好分析Agent和生成重新规划的Agent。他们之间在某些阶段可以并行，某些阶段是串行，由主管Agent统筹规划和管理。
